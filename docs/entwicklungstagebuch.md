**Cascade-Layer-Bug in `base.css` gefunden und behoben.** Beim Versuch, den Abstand zwischen Überschrift-Card und Nav-Cards per `mb-8`/`mb-12` zu vergrößern, blieb der sichtbare Abstand nahezu unverändert. Ursache per direkter Prüfung des von Vite ausgelieferten CSS bestätigt: Ein alter, aus dem electron-vite-Scaffold übernommener Reset (`*, *::before, *::after { margin: 0; ... }`) war nicht in `@layer base` eingebunden. Tailwind v4 nutzt CSS Cascade Layers (`@layer theme, base, components, utilities`) — nicht eingebundene („unlayered") Regeln gewinnen dabei grundsätzlich gegen jede Layer-Regel, unabhängig von Selektor-Spezifität. Der Reset hat dadurch potenziell **jede** `margin`-Utility-Klasse (`mb-*`, `mt-*` usw.) app-weit überstimmt, nicht nur an dieser einen Stelle. Zusätzlich war der Reset komplett redundant zu Tailwinds eigenem, bereits korrekt in `@layer base` eingebundenem Preflight (das setzt `box-sizing`, `margin: 0` und `list-style: none` für `ul`/`ol`/`menu` schon selbst). Fix: redundanten, unlayered Reset entfernt, das einzige zusätzliche Detail (`font-weight: normal`) korrekt in den bestehenden `@layer base`-Block verschoben. Nach dem Fix wirkt `mb-12` wie erwartet, per Screenshot bestätigt. `npm run typecheck` und `npm run lint` weiterhin sauber.

**Tatsächliche Ursache für die wiederholte `.editorconfig`-Verfälschung (CRLF statt LF, fehlende Abschluss-Newline) gefunden und dauerhaft behoben.** Bisher (Schritt 2, Schritt 6/7) jeweils nur Symptom mit `git checkout -- .editorconfig` weggewischt, ohne Ursache zu kennen. Diesmal gezielt geprüft: kein npm-Skript/ESLint/Prettier fasst die Datei an (Prettier kennt für `.editorconfig` keinen Parser, ESLint hat kein passendes Glob), `core.autocrlf` war weder lokal noch global im Repo gesetzt — die eigentliche Ursache liegt eine Ebene höher, in `C:\Program Files\Git\etc\gitconfig` (System-weite Git-for-Windows-Installation, Installer-Default `core.autocrlf = true`). Ohne eigene `.gitattributes` im Projekt greift dieser System-Default: Git checkt Text-Dateien bei jedem Checkout/Pull/Stash mit CRLF im Arbeitsbaum aus, obwohl das Repository selbst LF speichert (bestätigt über `git ls-files --eol .editorconfig` → `i/lf w/crlf`). Normalerweise unsichtbar, weil `git status`/`git diff` beim Vergleich automatisch zurückkonvertieren — sobald aber ein Tool oder Edit-Vorgang die CRLF-Bytes vom Datenträger tatsächlich in ein Commit übernimmt (z. B. bei einem breiteren `git add`), bleibt CRLF dauerhaft im Repository stehen. Wichtigste Entscheidungen:

- **Architekturfrage Main-Prozess vs. `shared/` diskutiert und zugunsten von `shared/` entschieden**: Der Nutzer wollte die Berechnung ursprünglich im Main-Prozess ansiedeln, mit der nachvollziehbaren Begründung, dass auch `AuswertungsPage` und die künftige verkürzte Ansicht dieselbe Logik brauchen. Dagegen sprach die gleichzeitige Anforderung „live", also Berechnung aus dem noch ungespeicherten Entwurf — den kennt der Main-Prozess grundsätzlich nicht, ohne ihn bei jeder Zelländerung per IPC zu übertragen. Lösung: plattformunabhängige reine Funktionen in `shared/auswertung.ts`, wie schon `shared/kalendertage.ts` seit Schritt 7 aus demselben Grund dort liegt — erreicht Wiederverwendung ohne den Live-Zielkonflikt, da der Renderer sie synchron aufrufen kann.
- **„Freie Tage" als eigene, einfachere Definition geklärt** (vorher offene Frage in `auswertung.md`): Anzahl der `Planeintrag`-Datensätze eines Mitarbeiters mit `kuerzel === '/'`, unabhängig vom Wochentag — nicht die Summe aus „Freie Samstage" und „Freie Sonntage und Feiertage" (die als eigene, engere Zeilen für die spätere `AuswertungsPage` bestehen bleiben). `auswertung.md` entsprechend aktualisiert.
